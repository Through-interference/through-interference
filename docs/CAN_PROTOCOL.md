# Протокол CANLINK v2

## USB-UART, 115200 8N1

Строки ASCII завершаются CR, LF или CRLF. Входная строка максимум 120 символов; превышение отклоняется целиком после разделителя, не исполняется усечённая команда. Полезные байты представлены HEX, поэтому нулевые байты и CR/LF внутри CAN-данных не меняются.

| Команда | Результат |
| --- | --- |
| `CAN OPEN` | Открыть или продлить приём на компьютере на 5 секунд. Клиент повторяет раз в 1,5 секунды. |
| `CAN CLOSE` | Закрыть приём, оставить недоставленные кадры в RAM. |
| `CAN TX t123200FF` | Отправить стандартный CAN ID 0x123, DLC2, данные 00 FF. `+CAN QUEUED` подтверждает только локальную очередь. |
| `CAN TX T1ABCDE0180011223344556677` | Расширенный ID 0x1ABCDE01, 8 байт. |
| `CAN TX r1238` / `R1ABCDE018` | RTR с требуемым DLC, без данных. |
| `CAN ACK 17` | Подтвердить приём USB-кадра с идентификатором доставки 17. |
| `CAN STAT` | Состояние очередей, радио, CAN, потерь и ошибок. |
| `CAN DIAG` | Только USB борта: фактическая CAN-скорость, состояние TWAI, TEC/REC, аппаратные ошибки, уровень RX и маршрутизация GPIO. |

Счётчики `CAN STAT` относятся к локальной плате. Поэтому `CAN_FAIL=0` на земле не подтверждает исправность CAN борта. Для проверки борта читать `CAN STAT` и `CAN DIAG` непосредственно через его USB. `CAN DIAG` на земле возвращает `ERROR: CAN_DIAG_AIR_ONLY`; в консоли `can>` команды `stat` относятся к земле, если выбран режим `ground`.

`CAN_READY=1` означает, что локальный драйвер CAN запущен; это не подтверждение доставки кадра или наличия CAN ACK. На земле `CAN_READY=0`. После ошибки первоначального запуска драйвер борта запускается повторно каждые 2 секунды.

Полученный кадр: `+CAN RX 17 t123200FF`. Пока компьютер не отправил `CAN ACK 17`, строка повторяется каждые 250 мс, кадр остаётся в очереди. Повторный ACK старого номера не извлекает следующий кадр. `tools.can_client.UsbReceiver` проверяет запись, помещает её в ограниченную очередь приложения, затем формирует ACK; повторы с тем же номером и данными повторно приложению не выдаются.

Заполнение очереди TX возвращает `ERROR: CAN_QUEUE_FULL`, закрытый приём `ERROR: CAN_CLOSED`, неверная запись `ERROR: CAN_FRAME`. Эти ответы не должны интерпретироваться как успешная отправка. Локальный OK, принятие радиопакета и результат выполнения команды БВС являются разными событиями.

Логи и AT-ответы могут приходить между CAN-строками. Приёмник должен разбирать только точный префикс и формат полезных данных. Один процесс владеет serial-портом: панель, консоль или тест, а не несколько одновременно.

Таймаут чтения serial не завершает строку: клиент сохраняет её фрагмент до CR/LF. Повреждённый ответ статуса отклоняется отдельно от ошибок порта. GUI подтверждает подключение только после получения `CAN STAT` с `ROLE=GROUND,OPEN=1`; отсутствие подтверждения за 6 секунд или роль `AIR` закрывает подключение.

## Локальная настройка

Сохранены `VER`, `CFG`, `RSSI`, `SNR`, `STAT`, `LINK`, `PWR`, `MOD`, `PRIMFREQ`, `BACKFREQ`, `KEY`, `SAVE`, `RST`. LINK проверяет локальный сервис; фактический радиопартнёр отражается в CAN STAT LINK. `CANBAUD 500000` реально меняет TWAI на бортовой плате, если её исходящая очередь свободна. На наземной плате физического CAN нет, эта операция отклоняется.

Радиопрофили и ключ задаются на обеих платах отдельно; согласование смены модуляции по старому текстовому OTA-протоколу не используется. При первичной настройке новой пары сгенерировать один случайный 128-битный AES-ключ на доверенном компьютере, применить одинаковые 32 HEX символа командой KEY к двум платам и выполнить SAVE. Не создавать независимые ключи на каждом конце. Нулевой ключ блокирует радио. Формат NVS ModemConfig сохранён; поля прежнего TDMA и антенного переключателя сохраняются только для совместимости хранения.

Резервная копия flash содержит ключи и должна храниться приватно. При откате приложения нельзя откатывать счётчики AES-GCM: восстанавливать только раздел приложения с сохранением актуальной NVS или заново сопрягать обе платы с новым случайным ключом. Полное восстановление старого снимка NVS под тем же ключом может повторить nonce.

## Радио

Земля отправляет POLL, борт после приёма отвечает RESPONSE. Оба несут исходящие данные и подтверждение предыдущего входящего пакета. Пустые опрос/ответ проверяют оба направления даже без команд. Максимум четыре CAN-кадра в одном пакете. До данных оба конца узнают текущие 64-битные сессии друг друга; пакет адресуется конкретной сессии получателя.

После AES-GCM-расшифрования двоичный заголовок имеет 36 байт:

| Смещение | Поле |
| --- | --- |
| 0 | Версия 2 |
| 1 | POLL=1, RESPONSE=2 |
| 2..9 | Случайная сессия отправителя, uint64 LE, ненулевая |
| 10..13 | Номер пакета данных, uint32 LE, 0 только для пустого пакета |
| 14..21 | Сессия адресата, uint64 LE, 0 только для начального пустого опроса |
| 22..29 | Подтверждаемая сессия, uint64 LE |
| 30..33 | Подтверждаемый номер пакета, uint32 LE |
| 34 | Количество CAN-кадров 0..4 |
| 35 | Готовность принять полезные данные, 0/1 |

Далее каждый кадр занимает 14 байт: CAN ID uint32 LE, флаги bit0 EXT/bit1 RTR, DLC, 8 байт данных. Неиспользуемый хвост заполняется нулями. Для RTR данные не передаются логически. Длина пакета ровно `36 + 14 * count`, до 92 байт. Неизвестная версия, тип, флаги, длины или ID отклоняются.

Внешняя оболочка существующего криптопротокола `E1|sender|counter|ciphertext_hex|tag_hex`. При повторе прикладной номер сохраняется, криптографический счётчик новый. На приёме проверяются аутентификация, криптопартнёр, счётчик и сессия адресата. Криптографические дубликаты отклоняются. Очередь отправителя освобождается только при подтверждении её сессии и номера. Прикладной повтор не выдаётся в USB/CAN; тот же номер с другим содержимым отвергается.

RX high-water mark хранится в RAM; после перезапуска старые кадры данных адресованы прежней случайной 64-битной сессии и не принимаются новой сессией. Исходящие nonce-счётчики резервируются в NVS блоками по 65536, до использования, остаток блока после перезапуска пропускается. Пустые опросы не пишут NVS.

При отсутствии ответа запрос повторяется. При длительном отсутствии партнёра и `FHSS 1` обе платы ищут его на основной/резервной частоте. `FHSS 0` возвращает модем на основную частоту и отключает автоматическое переключение до повторного включения. Флаг не задаёт синхронное расписание прыжков частоты. Таймаут ответа зависит от времени в эфире текущего профиля.

Ошибка перехода в RX помечает радио неготовым и запускает повторную инициализацию через 250 мс. Если инициализация не удалась, она повторяется через 2 секунды. Содержимое очередей и сессии CANLINK при этом сохраняется.

## Очереди и границы подтверждений

Исходящая радиочередь: 64 CAN-кадра на каждом конце, включая активную пачку. Очередь CAN TX на борту: 64. Очередь доставки USB на земле: 64. Аппаратная RX-очередь TWAI: 128. Отправитель сохраняет активную пачку при потере ACK. Приёмник принимает всю пачку в очередь назначения или не продвигает подтверждение. Компьютер без открытого приёма не получает новые пачки телеметрии, недоставленные USB-кадры не удаляются по таймауту.

Передача CAN неблокирующая, кадр хранится до TWAI TX_SUCCESS. Отсутствие CAN ACK и bus-off не останавливают радио/USB. Счётчики CAN_FAIL/BUS_OFF/CAN_DROP и QUEUE_REJECT позволяют отличить переполнение от плохого радио. Поток CAN, превышающий пропускную способность радио и ёмкость буферов, может теряться; потери не маскируются успешным ответом очереди.

Радио-ACK означает принятие в RAM-очередь назначения, а не выполнение команды БВС. При потере питания могут потеряться принятые, но ещё не выданные кадры. Если адресат сменил сессию, активная неподтверждённая пачка учитывается в UNCERTAIN и больше не пересылается в новую сессию, чтобы команда не выполнилась второй раз. Выводится `+CAN UNCERTAIN <count>`. Гарантии exactly-once через отключение питания нет. Для команд необходим собственный transaction ID/подтверждение выполнения в протоколе БВС, как в MAVLink.

Если локальный USB-ответ о постановке команды в очередь не пришёл вовремя, клиент не может определить результат и блокирует дальнейшие send до переподключения. Это предотвращает принятие запоздалого ACK за подтверждение другой команды.

MAVLink v1/v2 переносится только в том виде, в котором он представлен в CAN-кадрах. Этот протокол не реализует DroneCAN Serial PassThrough и не назначает произвольному автопилоту новые CAN ID. Совместимость с реальным автопилотом проверяется отдельно на его CAN-интерфейсе.
