# Проверка демонстрации, 2026-11-09

## Результаты ревью

Два независимых ревью проверили прошивку, транспорт компьютера, скрипты и воспроизводимость README. Блокирующих замечаний после исправлений не осталось.

Исправлены:

- Для Linux добавлен SocketCAN через штатный драйвер gs_usb. Драйвер USB для macOS отделён от Linux.
- Автотест использует уникальные пакеты для каждого запуска. Старые кадры не дают ложный PASS, Ctrl+C завершает тест кодом 130.
- Настройка CAN сбрасывает активные listen-only/loopback/FD режимы, не задавая неподдерживаемые флаги Classical CAN адаптеру.
- Для новой пары есть воспроизводимая настройка обоих UART-портов с одним случайным общим ключом. Фиксированный ключ из bind.py удалён.
- Проверка отказов заранее проверяет GFSK250 и восстанавливает его при завершении. Ошибки закрытия адаптера не мешают закрытию других ресурсов и записи JSON-отчёта.
- Исправлены два предупреждения GCC о знаковости размеров CAN-пакета. Размеры и формат пакетов не изменены.
- README описывает подготовку окружения отдельно для демонстрации и тестов. Из сценариев запуска убраны пути конкретного Mac.

## Воспроизведение программной проверки Linux

Из корня проекта с работающим Docker:

```bash
docker build -t bas-can-linux-check -f tests/linux/Dockerfile .
docker run --rm --mount type=bind,src="$PWD",dst=/source,readonly \
  bas-can-linux-check bash /source/tests/linux/run.sh
```

Контейнер создаёт новое окружение и копирует только исходники; папка проекта подключается только для чтения. Проверка не открывает USB и не заменяет аппаратную демонстрацию.

## Пределы проверки

Docker-ядро на данном Mac не поддерживает AF_CAN. Поэтому физический CANable и настоящий SocketCAN/vcan на Linux в этой среде не проверялись. Отображение кадров и отказов Linux-транспорта проверено с python-can VirtualBus и контролируемыми ответами ip. Для аппаратной проверки на Linux выполнить сценарий README с can-utils или start-demo.sh --demo.

Дальность радио, RF-помехи, принудительный физический bus-off и совместимость с реальным автопилотом в этот прогон не входят. Исходный временный сбой CAN восстановился и больше не воспроизводится; точная причина не установлена. Описанные тесты подтверждают текущую работу стенда, но не доказывают причину того сбоя.

Ограничения RESTORE и неактивного флага FHSS явно описаны в README.
